**Status: adapter built and empirically verified. Not wired into the turn
loop** — the lead scoped this task to the invocation layer only; router/
ladder wiring stays blocked behind F46/F50 (fixed since, per `docs/TASKS.md`
— "Findings register: close F46 and F50" — but re-wiring `nova/app.py` to

Companion to `docs/THREAT_MODEL_CLAUDE_FALLTHROUGH.md` (nova-security's

(the module itself — read its docstring first; this document is the short

## Interface

```python
async def ask(
    prompt: str, *, egress: Egress, audit: AuditLog,
    timeout_s: float = 30.0, model: str = "sonnet",
) -> ClaudeAnswer | ClaudeProposal | ClaudeFailure

@dataclass(frozen=True)
class ClaudeAnswer:
    text: str

@dataclass(frozen=True)
class ClaudeProposal:
    skill_name: str
    params: dict[str, Any]

@dataclass(frozen=True)
class ClaudeFailure:
    reason: str    # cli_not_found | spawn_failed | timeout | process_error | model_error | unparseable_output
    detail: str = ""
```

`prompt` must already contain everything Claude needs (transcript + the
registered skill names/descriptions) — composing that is the caller's job,
per the plan's "minimal context" list. This module owns only the
output-format contract (its own system prompt + `--json-schema`) and the
process lifecycle.

## Finding 1 — does the spawned process have tools? Verified, not configured

nova-security's threat model named this the load-bearing question and
required proof, not a flag choice. Three real-subprocess experiments (all
reproducible via `scripts/probe_claude_arm.py`):

1. **A/B, same prompt, only `--tools` differs.** "Create marker.txt with
   your Write tool":
   - `--tools ""`: model's text claimed success; **zero tool calls
     attempted** (`permission_denials: []` — not denied, never tried); no
     file appeared.
   - default tools: model **did** attempt a real `Write` call — visible in
     `permission_denials` with the exact `tool_name`/`file_path`/`content`
     — denied by the headless permission system (no
     `--dangerously-skip-permissions`, ever). No file appeared here either,
     but because a *second, weaker* layer caught an actual attempt.
2. **Hostile/injected prompt** asking for a real Bash command and a real
   Write-tool file: zero new files, `permission_denials: []`, model
   correctly identified it as an injection attempt (behavioral bonus, not
   the control being relied on).
3. **The model's self-report about its own tools is not trustworthy
   evidence.** Asked directly, under `--tools ""`, it *fabricated* a
   12-tool list (Bash, PowerShell, Read, Edit, Write, Glob, Grep, WebFetch,
   WebSearch, TodoWrite, Task, NotebookEdit) — longer than what it reported
   under default tools. This is why the verification above is anchored to
   observable side effects (files on disk, a real `permission_denials`
   entry naming an attempted tool), never to what the model claims about
   itself.

**Conclusion: `--tools ""` structurally removes the tool schema at the
model level, one layer earlier than the permission system** — the correct
place for this control to live, per finding 1's own reasoning (a permission
check is a second opinion asked *of* something that has the capability; a
missing tool schema means the capability was never offered).

## Verification performed

`scripts/probe_claude_arm.py` (real CLI, real Max-plan auth, not mocked):

1. Benign question → `ClaudeAnswer`. Pass.
2. "open notepad for me" (with a fake two-skill list in the prompt) →
   `ClaudeProposal(skill_name="open_app", params={"app": "notepad"})`. Pass.
3. Hostile prompt → zero new files in a real scratch directory. Pass.
4. Simulated missing CLI (`find_cli()` monkeypatched to raise) →
   `ClaudeFailure(reason="cli_not_found")`, no exception escapes `ask()`.
   Pass.

Separately (not in the script, run manually against `ask()` directly):
timeout+kill against a real in-flight `opus` call with `timeout_s=0.5` —
`ClaudeFailure(reason="timeout")` returned, and `tasklist /FI "PID eq
<killed pid>"` confirmed the process was gone. Notable: `proc.wait()` after
`proc.kill()` did not return within a 5s bound even though the process was
verifiably dead (`tasklist` confirmed) — a known Windows/`ProactorEventLoop`
quirk. The module does not treat that as "kill failed"; `taskkill /T /F`
runs unconditionally regardless of whether the post-kill `wait()` returned,
and that exit is what's actually trusted.

## F59 — the env-scrub requirement, resolved

The threat model's finding 8 asks for `ANTHROPIC_API_KEY` /
`CLAUDE_CODE_USE_BEDROCK` / `CLAUDE_CODE_USE_VERTEX` to be scrubbed from the
child's environment. This module's first version left it unimplemented,
flagged rather than worked around, because implementing it means reading
`os.environ`, and `tests/test_source_hygiene.py::test_module_does_not_read_
os_environ` is a zero-exemption, repo-wide static tripwire on exactly that.

The lead proposed exempting this whole file from the rule. nova-security
agreed with the reasoning (containing a child's environment is not the same
category of thing as reading config-by-environment) but ruled the scope too
wide — *"nothing would stop that file from later reading an unrelated var
and using its value."* Built to the ruling's actual shape instead:
`_child_env()` touches only **presence/absence** of the closed, literal
`_ENV_VARS_TO_SCRUB` set via `dict.pop(name, None)` — it never reads or
branches on what any variable is *set to*, and it is the only place in the
file that names `os.environ` at all. `ask()` now passes `env=_child_env()`
to the one spawn call.

**Coordination note, not yet fully landed:** `tests/test_source_hygiene.py`
needs a matching `ENVIRON_ALLOWLIST` entry (size-pinned at one) plus a
structural test constraining *how* this file touches the environment —
nova-tester's file, routed by the lead, not edited here. Until that lands,
`test_module_does_not_read_os_environ[brain\claude_arm.py]` is expected to
be red — a known, coordinated, temporary state, not a surprise regression.

## F61 — the resolved CLI path is audited on every invocation

`find_cli()` trusts PATH search order with no containment check — a
`claude`/`claude.cmd` planted earlier on PATH would be silently spawned.
nova-security explicitly did not want an `open_app`-style curated-directory
allowlist here (right for Program Files, wrong for an npm-installed tool a
global `npm install` can relocate) and instead asked for the resolved path
to be logged, so a substitution is visible after the fact rather than
never. `ask()` records a `claude_arm.invoke` audit event (`cli_path`,
`model`) immediately after `find_cli()` succeeds, before
`release_for_process()` or the spawn. Verified against a real run:
`AuditLog`'s own redaction rewrote the resolved path's username segment
(`C:\Users\[USER]\AppData\Roaming\npm\claude.CMD`) automatically, and each
record hash-chained correctly.

`audit: AuditLog` is a separate parameter from `egress: Egress` — `Egress`
does not expose its internal `AuditLog` publicly, and adding a public
accessor to `nova/security/egress.py` for this was judged unnecessary
surface to add to a security-critical file this module doesn't otherwise
need to touch.
