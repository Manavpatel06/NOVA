# ADR 0006 (open question): memory does not return to baseline after unload

**Status: still an open question, not a decision — but a much better-understood one.** Finding **F16** in `docs/TASKS.md` (HIGH severity). nova-dev-core's diagnosis (`docs/F16_MEMORY_RETENTION.md`) has answered most of what this document originally listed as unknown; two sub-questions remain genuinely open (VRAM creep over long sessions, and whether to eventually pursue a process-boundary fix). This revision folds that diagnosis in. **No design resolution exists yet** — do not read anything below as one, including the governor's current ceiling value, which is a provisional accommodation, not a closed decision (see the last section).

## The measurement, updated and corrected

Original (lead, one 3-turn run): RSS 59.4 → 1254.6 → 912.9 MB; VRAM 264 → 2570 → 566 MiB.

**The VRAM figures in that original run were contaminated** — `nvidia-smi` reports machine-wide GPU memory, not per-process (Windows' WDDM driver mode doesn't expose reliable per-process VRAM accounting at all: `nvidia-smi --query-compute-apps=pid,used_memory` returns `[N/A]` for every process on this machine). Another agent's GPU process was resident during that measurement. Corrected, reproduced twice by nova-accuracy: **VRAM retention is ~103 MiB, not ~300 MiB.** Host RSS retention (~850 MB) was not affected by this contamination and stands.

## What's now known, not just hypothesized (`docs/F16_MEMORY_RETENTION.md`, nova-dev-core)

1. **It's native library memory, not a Python reference leak — confirmed, not assumed.** `tracemalloc` shows only ~23-25 MB tracked after Whisper unloads, against ~737 MB of real RSS above baseline at the same moment: Python's own allocator tracker accounts for ~3% of the retained memory. The rest was never allocated through Python's allocator, so `del`/`gc.collect()` structurally cannot see or release it.
2. **The specific mechanism is identified, not guessed.** `ctranslate2.dll` (4.8.1) contains the strings `CT2_CUDA_ALLOCATOR` and `CT2_CUDA_CACHING_ALLOCATOR_CONFIG` — confirmed by grepping the binary directly. CTranslate2 ships a **caching allocator by design**: memory it frees internally is kept in a pool sized to the largest allocation seen, for reuse on the next call, rather than returned to the OS/driver. This is a deliberate CTranslate2 performance optimization (avoiding repeated `cudaMalloc`/`cudaFree` overhead), not a bug in CTranslate2 and not a bug in `Transcriber.unload()` — the pool lives one layer below anything Python's `gc` can walk.
3. **Host RSS: a floor, not a leak — confirmed over 10 cycles, not the original 3.** One process, 10 sequential load→transcribe→unload cycles: RSS went 767.4 → (stable ~710-732 MB band) → 712.6 MB. A slight *decrease* from cycle 1, then flat within ~20 MB for the remaining 9. No linear climb. The floor is set by the *first* real inference, not accumulated per call — a second test (one load, three `transcribe()` calls, one unload) ended *below* the single-transcribe floor from the same run series.
4. **Kokoro/onnxruntime is not part of the VRAM story at all.** This machine's onnxruntime has no CUDA execution provider installed (`get_available_providers()` returns CPU/Azure only) — Kokoro runs entirely on CPU, confirmed by a zero-CUDA-DLL import diff. Kokoro has its own, much smaller host-RSS floor (~111-135 MB) and — unlike Whisper — its `unload()` **does** release most of what it used (~76%). The two components' floors are additive: predicted combined floor (867.1 MB) matched an actual combined-process measurement (862.5 MB) within 5 MB, closing the gap between earlier isolated-component numbers and the lead's/nova-dev-stt's full-app numbers.
5. **The achievable idle, stated precisely:** `docs/ARCHITECTURE.md`'s "< 300 MB RSS" idle target holds exactly once — cold, before either model has ever run (measured 22-57 MB across every test in this investigation). It does not hold as a *return-to-idle-after-use* claim, structurally, given what CTranslate2 exposes today. Once `Transcriber.transcribe()` has run at least once in a process, that process's floor is ~735-770 MB (Whisper alone) or ~850-900 MB (Whisper + Kokoro, both used at least once) and nothing `unload()` does today can lower it.

## What's still genuinely open

- **VRAM shows a slower, real drift that has not obviously plateaued**: 367 → 439 MiB over 10 cycles, roughly +7-8 MiB/cycle. Small in absolute terms; 10 cycles is explicitly stated as not enough to rule out a slow climb over a full day of real use. nova-dev-core's own recommendation: extend to 30-50 cycles before calling this closed. **Not done yet.**
- **The lead's original 566 MiB full-app VRAM figure could not be reproduced** by a minimal two-component isolation script (which got 367 MiB, matching Whisper-alone). Candidates considered and not ruled out: more governor-triggered reload cycles across a longer real session, or `nvidia-smi` measurement noise in a busier/longer process. Recorded as genuinely open, not closed with a guess.
- **Whether a process-boundary fix (running Whisper/Kokoro in a killable subprocess, trading reload latency for real OS-level reclamation) is worth pursuing is entirely undecided.** nova-dev-core identified it as the only lever that could lower the floor further — Python-level: checked `dir(ctranslate2)` for a cache-release call, found none — but explicitly flagged it as "a materially bigger change than the governor... the lead's design conversation, not started here." No decision has been made for or against it.

## The one real tuning decision made so far — provisional, not a resolution

`nova/config.py`'s `GovernorConfig.rss_ceiling_mb` defaults to **900.0** — set at, not below, the measured combined floor (~850-900 MB), rather than at `docs/ARCHITECTURE.md`'s original "< 300 MB" idle target. This is a deliberate acknowledgment that a ceiling the library structurally cannot reach would make `Governor.check_once()` either thrash (repeatedly unloading and immediately reloading with no lasting effect) or report an honest, permanent "still over ceiling, nothing left to free" — neither of which serves anyone. `Governor`'s own mechanism was verified correct independent of this question (it withholds unloads mid-turn and reports honestly when a ceiling can't be reached).

**This is not the same as deciding 900 MB is the right long-term number.** It's a value chosen to match today's measured reality so the governor's own logic isn't fighting a target it can't hit — not a claim that ~900 MB idle is an acceptable place to stop. Revisit once the VRAM-creep question closes (if VRAM keeps climbing per-cycle without bound, no RSS ceiling addresses that) and once someone actually decides whether the process-boundary approach is worth its cost. Diagnosis-only was the lead's explicit instruction for this round (`docs/F16_MEMORY_RETENTION.md`'s owner line); no fix or workaround was in scope, and none has been chosen.
