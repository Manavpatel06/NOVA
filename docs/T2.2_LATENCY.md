# T2.2 — Turn latency, decomposed and measured

**Status: measured, not modelled.** Real hardware (RTX 5060, real speakers),
real models (`large-v3-turbo` cuda/float16, Kokoro ONNX), real bus
instrumentation. `scripts/measure_latency.py` runs the exact production path
(`NovaApp.run_turn()`) with Kokoro-synthesized speech standing in for a live
mic capture — same limitation `scripts/probe_turn.py` already states: this
proves the wired pipeline's latency, not the hotkey-to-mic path.

## Why this exists

Manav's only prior latency datum was subjective: "~5-8s, felt slow" from the
first real spoken turn on 2026-08-20 (`docs/M2_OPEN_BRAIN_PLAN.md`). That
number conflates a one-time model-load cost with steady-state, and conflates
"turn finished" with "NOVA started talking" — two things that feel completely
different to a human waiting for a response. This decomposes both.

## Instrumentation

`nova/telemetry.py` (`LatencyMark`, `TOPIC_LATENCY_MARK`, `LatencyLog`) — bus
marks published at each stage boundary, not a number computed and logged in
one place. Stage order:

```
ptt_end -> capture_drained -> stt_start -> transcript_ready
        -> route_decided -> skill_returned -> synth_returned -> first_audio_out
```

**`first_audio_out` is measured where the plan asked for it to be measured:**
`nova/audio/player.py`'s `Player.play()` takes an `on_first_frame` callback,
invoked from the real `sounddevice` audio callback thread the first time a
real (non-empty, non-cancelled) block of PCM is handed to the output device —
not when `Synthesizer.say()` returns. `synth_returned` is kept as its own
mark specifically so a gap between it and `first_audio_out` is visible
instead of hidden inside one "TTS" number.

This replaced `run_turn()`'s prior ad hoc `timings` dict / `_log_timings()` —
having both would have been two differently-computed answers to "how long did
this take," which is exactly what the constitution's "one source of truth per
invariant" rule exists to prevent.

**A note on `run_turn()`'s own wall-clock time vs. this metric:** `run_turn()`
does not return until `Player.play()`'s full clip finishes playing (`_speak()`
awaits it to completion). So `wall time` (when `run_turn()` returns) is
noticeably larger than `total` (first mark to `first_audio_out`) — the gap is
the reply's own speech duration (~1.6-1.8s for "It's H:MM AM/PM."), not
hidden latency. `total` is the number that answers "how long before Manav
hears anything," which is what this task was asked to produce.

## Results

Phrase: **"what time is it"** — a READ-tier skill, matching the plan's budget
target. `time`/route/skill logic itself measured in the noise (below).

### First turn (cold process — nothing loaded yet)

Three independent cold-process runs (a fresh Python process each time, not
three turns in one process — model loads are process-scoped, so this is the
only way to sample "first turn" more than once):

| Run | stt_start→transcript_ready (Whisper load+transcribe) | skill_returned→synth_returned (Kokoro load+synth) | synth_returned→first_audio_out | **total (first mark→first_audio_out)** |
|---|---|---|---|---|
| 1 | 3.101s | 1.430s | 0.286s | **4.825s** |
| 2 | 2.977s | 1.503s | 0.183s | **4.783s** |
| 3 | 2.882s | 1.327s | (not captured this run) | **4.502s** |

**First-turn total: 4.50-4.83s** (n=3, real range, not modelled).

The first run of this script (discarded, not in the table above) measured
`skill_returned->synth_returned` at 0.469s — matching the *steady-state*
number almost exactly. That was contamination, not a fast Kokoro load: the
script's own helper for fabricating the "captured audio" input was calling
`app.synth.say()` — the *same* Synthesizer instance the turn loop uses to
speak the reply — before timing started, so Kokoro was already warm by the
time the "first turn" it was supposed to measure began. Fixed by giving the
script a separate, throwaway `Synthesizer()` instance for generating input
phrases (`scripts/measure_latency.py`'s `_synthesized_16k_pcm` docstring).
Recorded here because it is exactly the kind of single-run, uninspected
number this project has been burned by twice before (`docs/TASKS.md`) — the
fix was catching it against a second run that didn't reproduce it, not
trusting the first number.

This also lines up with Manav's original report: first-turn `total` (4.5-4.8s)
plus that reply's own ~1.6-1.8s speech duration (the wall/total gap explained
above) is a **6.1-6.6s wall time to fully finish speaking** — squarely inside
his "~5-8s, felt slow." **The turn that felt slow was very likely the
cold-load turn, not a representative steady-state one.**

### Steady state (8 further turns, same warm process)

| Stage | min | max | mean |
|---|---|---|---|
| stt_start→transcript_ready (Whisper transcribe) | 0.465s | 0.495s | 0.479s |
| transcript_ready→route_decided (router) | 0.0004s | 0.0009s | ~0.0005s |
| route_decided→skill_returned (`time` skill) | 0.007s | 0.009s | 0.008s |
| skill_returned→synth_returned (Kokoro synth) | 0.403s | 0.424s | 0.416s |
| synth_returned→first_audio_out (playback start) | 0.176s | 0.182s | 0.179s |
| **total (first mark→first_audio_out)** | **1.071s** | **1.102s** | **1.082s** |

n=8, one warm process, consecutive turns.

## Does the 1.5s budget survive contact with the data?

**Steady state: yes, comfortably.** 1.08s mean, 1.10s worst-of-8 — 27-29%
headroom under the 1.5s target for a READ skill.

**First turn: no, not close.** 4.5-4.8s is roughly 3-3.5x the budget. The
plan already scoped the 1.5s target to steady state, so this isn't a broken
promise — but it does mean **the number a new user (or NOVA restarting after
being idle long enough to unload, F16/T1.2) actually experiences on their
first utterance is 3-4x slower than the number this budget describes**, and
that gap is exactly what the pre-warm ADR below is about.

## Two things nobody was watching for

1. **Route+skill is far cheaper than the plan assumed.** The plan's own text
   says *"`time` currently returns in ~0.08s, so the budget is dominated by
   transcription and synthesis."* Measured: route+skill combined is
   **~8ms**, not ~80ms — an order of magnitude faster than the number the
   budget reasoning was built on. This doesn't change the conclusion (STT +
   TTS still dominate), it just means the "budget is dominated by
   transcription/synthesis" claim is *more* true than the plan's own napkin
   figure suggested, not less.
2. **Playback-start latency (`synth_returned->first_audio_out`) is a real,
   stable ~180ms — about 17% of the entire steady-state total** — and it is
   pure output-device pipeline (`sounddevice.OutputStream` creation +
   first callback), not synthesis compute; `synth_returned` is marked the
   instant `Synthesizer.say()` returns, before `Player.play()` is even
   called. `nova/audio/output.py`/`nova/audio/player.py` construct the
   `OutputStream` without an explicit `latency=` argument anywhere, so this
   is `sounddevice`'s default (high-latency-safe) buffering, unmeasured
   until now. Not fixed here — T2.2 is instrumentation before optimisation
   — but it is the single largest chunk of the steady-state total that isn't
   STT or TTS compute, and the most likely first thing to tune if steady
   state ever needs to be faster than 1.08s.

## What this does not measure

- The real hotkey→mic capture path (`_on_ptt_end`'s `capture_drained` mark
  exists for this, but this script calls `run_turn()` directly and never
  produces a `ptt_end`/`capture_drained` mark at all — see
  `scripts/measure_latency.py`'s module docstring).
- Wake-word-triggered turns (F26/F27/F28-gated, not wired in yet).
- Any turn that goes through Claude fallthrough (T2.4, not built yet) — that
  gets its own latency budget per the plan, deliberately.
